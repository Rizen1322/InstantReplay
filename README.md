# Aura

Аналог NVIDIA ShadowPlay Instant Replay: постоянная фоновая запись экрана в кольцевой буфер RAM, сохранение последних N минут по хоткею. C# / .NET 9 / WPF, отдельное приложение, без Steam и сторонних сервисов.

`src/Aura` — актуальное приложение. `src/InstantReplay` — прежняя версия на WinUI 3, оставлена
для сверки на время переезда; ядро (захват, кодировщик, звук, хоткеи, хранилище) у них общее
по происхождению, но правки вносятся только в `src/Aura`.

## Сборка

Требуется **Windows 10 2004+ / Windows 11** и .NET 9 SDK (или Visual Studio 2022 с рабочей
нагрузкой «Разработка классических приложений .NET»).

```
dotnet build -c Release -r win-x64 src/Aura/Aura.csproj
```

Windows App SDK больше не нужен: WPF даёт интерфейс, а проекции WinRT
(`Windows.Graphics.Capture`, `Windows.Storage`) приходят из самого TFM
`net9.0-windows10.0.22621.0`.

Для отладки вёрстки без запроса прав администратора собирается вариант с обычным манифестом,
и можно открыть приложение сразу на нужном разделе:

```
dotnet build src/Aura/Aura.csproj -p:ApplicationManifest=app.debug.manifest -o <папка>
```
```
Aura.exe --dev --page capture
```

`--dev` поднимает копию рядом с уже запущенной (обычно вторая копия просто показывает
окно первой), `--page <раздел>` открывает нужный раздел сразу: `overview`, `clips`,
`capture`, `keys`, `files`, `app`, `system`.

| Иконки (контуры 24×24) | `Theme/Icons.xaml` |
| Карточка записи | `Theme/Clips.xaml` |
| Свои элементы (`Icon`, `IconTile`, `Switch`, `Segmented`, `KeyCaps`) | `Controls/Primitives.cs` |
| Окно: своя шапка, боковая колонка, масштаб, навигация | `MainWindow.xaml(.cs)` |
| Разделы | `Views/*Page.xaml(.cs)` |
| Уведомление поверх игры | `Notifications/ToastWindow.xaml(.cs)` |

Решения, которые важно не потерять:

- **Шрифты вшиты в сборку** (`Fonts/*.ttf`): Golos Text для интерфейса и Onest для заголовков —
  у обеих кириллица нарисована, а не растянута из латиницы. Статические начертания нарезаны из
  вариативных, потому что WPF вариативные оси не поддерживает и показал бы всё одним весом.
- **Тема меняется подменой `MergedDictionaries[0]`**, поэтому все стили ссылаются на цвета
  через `DynamicResource`. `StaticResource` в теме сломает переключение на лету.
- **Масштаб интерфейса** — `ScaleTransform` на корневой сетке окна (`--page` `Приложение` →
  «Размер интерфейса»). Значение 0 в настройках = подобрать по высоте экрана: Full HD обычный,
  2K крупнее, 4K ещё крупнее.
- **Компактный режим** включается по ширине ОКНА (< 880 px), а не экрана: боковая колонка
  сворачивается в иконки, подписи групп превращаются в разделители.
- **Ползунки подписываются в конструкторе, а не в разметке**: присвоение `Minimum` при разборе
  XAML уже поднимает `ValueChanged`, и обработчик падал на элементах, которых ещё нет.
- **`SelectionChanged` и `Click` требуют разных делегатов** — на одну логику заведены две обёртки.
- **Раздел, который не собрался, показывает ошибку, а не пустой экран** (`Views/BrokenPage.cs`).
- **Строки настроек — `Controls/AdaptiveRow.cs`**: когда окно сужается, управление уезжает под
  подпись, а не обрезается краем. Свёрнутая боковая колонка ужимает поля, иначе переключатель
  шириной 44 px не влезал в 64 px колонки.
- **Плашка «есть несохранённое» живёт в окне** (`MainWindow.ShowApplyBar`), а не в конце
  страницы: до неё не нужно долистывать.
- **AV1 на Windows 10 кодируется, но не сохраняется.** Видеокарта RTX 40+ отдаёт поток AV1,
  а MP4-мультиплексор Windows 10 про него не знает: `SinkWriter` падает с
  `MF_E_SINK_HEADERS_NOT_FOUND` уже на финализации — то есть буфер пишется, а каждое
  сохранение проваливается. `VideoEncoder.CanSaveToMp4()` считает кодек доступным только
  если система умеет его упаковать (для AV1 — сборка Windows ≥ 22000); на «Захвате» и в
  «Системе» причина пишется прямо, а при старте приложение само уводит с такого кодека.
- **Обрезка и сжатие — внешние программы.** «Обрезать» открывает клип в LosslessCut (режет
  без перекодирования), «Сжать для Discord» зовёт ffmpeg, который лежит рядом с ним. Пути
  ищутся автоматически по обычным местам установки и спрашиваются один раз.
- **Перетаскивание клипа** сделано присоединяемым свойством `Controls/DragFile.cs`: шаблон
  карточки живёт в словаре ресурсов, code-behind у него нет.
- **`GlobalUsings.cs` вместо `ImplicitUsings`**: временный проект, который MSBuild собирает под
  XAML (`Aura_*_wpftmp.csproj`), неявные using'и наследует не полностью.

## Архитектура конвейера

```
Windows.Graphics.Capture (BGRA, VRAM)
        │  frame.SystemRelativeTime (QPC-тики) — общая шкала времени
        ▼
ID3D11VideoProcessor  →  NV12 + масштабирование (VRAM, без hwdownload)
        ▼
HW MFT-энкодер (NVENC / AMF / QuickSync через MFTEnumEx MFT_ENUM_FLAG_HARDWARE)
        ▼
ReplayVideoBuffer — кольцевой RAM-буфер СЖАТЫХ кадров
        │                              WASAPI loopback + mic (NAudio)
        │                                      ▼
        │                              AudioMixerEngine — активный микшер:
        │                              поток по QPC каждые 10 мс, тишина-заполнение,
        │                              обе дорожки раздельно → ReplayAudioBuffer
        ▼
SaveReplay(): мгновенный снимок буферов → ReplaySaver (фон):
SinkWriter, видео passthrough (remux без перекодирования), PCM→AAC
→ Videos/<Игра>/replay_YYYY-MM-DD_HH-mm.mp4
```

Ключевые решения (в т.ч. выстраданные ранее грабли):

- **Кадр не покидает VRAM до энкодера.** hwdownload (GPU→RAM) — главный пожиратель CPU, его нет вообще: WGC-текстура → VideoProcessor → NVENC, всё в видеопамяти. В RAM попадает только сжатый битстрим (десятки МБ/мин вместо гигабайт).
- **Буфер хранит сжатое видео, файл = remux.** Сохранение 5-минутного клипа — доли секунды, без нагрузки на GPU.
- **Подачу в SinkWriter НЕ ограничиваем искусственно** (`WriteDrain` в `ReplaySaver`). Тормозим только если видно, что писатель реально захлебнулся — по его собственной очереди (`IMFSinkWriter::GetStatistics`, `ByteCountQueued`), с потолком ожидания «как если бы диск давал 60 МБ/с». Здесь уже собрали три грабли: фиксированный потолок 220 МБ/с (угадан, съедал 2.8 с из 3.4 с на замерах), обратная связь по размеру файла (размер растущего файла отстаёт рывками — клип 317 МБ сохранялся 102 секунды) и та же фиксированная подача в роли «запасной» (обёртка статистику не отдаёт, и запасной режим стал основным). Память защищена не паузами, а тем, что кадры возвращаются в пул сразу после записи.
- **В игре запись файла уходит в фоновый режим ввода-вывода** (`THREAD_MODE_BACKGROUND_BEGIN`): Windows опускает потоку приоритет ДИСКОВЫХ операций, и залп в сотни мегабайт не отбирает диск у игры. На рабочем столе режим не включается — там тормозить сохранение незачем. Обычный `ThreadPriority.BelowNormal` на дисковую очередь не влияет вообще.
- **Прогресс сохранения** виден в шапке окна («Сохранение… 45%»).
- **Аудио — активный микшер, не пассивное чтение WASAPI.** WASAPI loopback молчит в тишине; микшер идёт по системным часам (QPC, та же шкала, что у видеокадров WGC) с шагом 10 мс и добивает недостачу тишиной → непрерывный PCM без рассинхрона, AAC-энкодер получает готовый поток.
- **Звук лежит на своей арене, как и видео.** Микшер отдаёт блок ссылкой на свои
  рабочие массивы, валидные только на время вызова (тот же контракт, что у
  `EncodedFrame`), а буфер копирует данные в две плоские арены — по одной на дорожку.
  Раньше на каждые 10 мс выделялась свежая пара массивов: двести штук в секунду, и
  трёхминутный буфер держал живыми под сорок тысяч объектов во втором поколении кучи —
  ровно там, где сборка мусора даёт паузы конвейеру. Сведение дорожек тоже больше не
  выделяет: вместо селектора, возвращавшего массив, вызывающий подставляет готовый
  приёмник (`AudioBlock.Mix`). Тесты `ПриёмБлоковНеВыделяетПамять` и
  `СведениеДорожекНеВыделяетПамять` держат это свойство.
- **Кольцевой буфер вытесняет по времени и режется по keyframe** (GOP = 2 сек через ICodecAPI): UI показывает ровно то, что реально сохранится, а клип всегда начинается с ключевого кадра.
- **CsWinRT-интероп** с `IGraphicsCaptureItemInterop` / `IDirect3DDxgiInterfaceAccess` — через `RoGetActivationFactory` + `Marshal.GetObjectForIUnknown` / `FromAbi` (не `.As<T>()`).
- **Жёлтая рамка записи убирается через package identity, а не через `IsBorderRequired`.** Свойство закрыто возможностью `graphicsCaptureWithoutBorder`, а объявить её можно только в манифесте ПАКЕТА — у неупакованного процесса `RequestAccessAsync(Borderless)` отвечает `DeniedByUser`, и присвоение `IsBorderRequired = false` при этом проходит без ошибки и читается обратно как `false`: по коду всё «в порядке», а рамка на экране есть. Обратное чтение свойства проверкой не является — достоверен только итог запроса права (`CaptureAccess.BorderlessGranted`). Identity даёт sparse-пакет (`packaging/AppxManifest.xml`, собирается `packaging/build_identity_package.ps1`): он содержит только манифест с возможностью, привязывается к папке приложения через `-ExternalLocation` и регистрируется установщиком, а элемент `msix` в `app.manifest` связывает с ним exe. Диалога согласия у системы для классических приложений нет — запись согласия заводится в состоянии `Prompt`, решение принимается на странице `ms-settings:privacy-graphicscapturewithoutborder`, которую приложение открывает один раз, если права нет. Пакет должен быть подписан сертификатом, доверенным на машине (`LocalMachine\TrustedPeople`), иначе регистрация падает с `0x800B0109`.
- **Хоткеи** — низкоуровневый хук `WH_KEYBOARD_LL` в отдельном потоке: комбинация ловится до игры, обработка уводится в ThreadPool (<1 мс в хуке). Рядом на том же потоке и в том же цикле сообщений стоит `WH_MOUSE_LL` — колесо и две боковые кнопки (`Mouse3`/`Mouse4`/`Mouse5`) назначаются как обычные клавиши, в том числе с модификаторами. Коды взяты настоящие (`VK_MBUTTON`, `VK_XBUTTON1/2`): клавиатурный хук их не выдаёт никогда, поэтому одна карта сочетаний обслуживает и клавиши, и мышь. **Левой и правой в списке нет намеренно** — перехват отобрал бы у человека мышь. В хуке мыши первым делом идёт отбор по типу сообщения: туда прилетает каждое движение, сотни событий в секунду.
- **Уведомления** — WinUI-окно поверх всех окон, Acrylic, fade+slide-анимации, click-through, не отбирает фокус. **Белая рамка** системного окна убрана через `DwmSetWindowAttribute(DWMWA_BORDER_COLOR, DWMWA_COLOR_NONE)` — это единственный работающий способ для WinUI 3.
- **Списки игр и исключений дополняются файлом, а не только релизом.** Встроенные значения (`Core/GameDetection/GameDatabase.cs`) — база, которая работает всегда; поверх неё накладываются `games.json` рядом с приложением и `%LocalAppData%\Aura\games.json` (второй главнее). Файл содержит только ОТЛИЧИЯ: `games` добавляет или переименовывает игру, `ignored` добавляет исключение, `allowed` снимает встроенное (кому-то нужна папка «OBS»). Отсутствие файла и сломанный JSON не ломают ничего — детектор работает на встроенных значениях. Разрешённое имя **кэшируется по процессу**: движок спрашивает игру раз в две секунды, а `MainModule` и `FileVersionInfo` для незнакомой программы стоят дорого.

- **Статистика хранилища** считается по индексу папки (`Core/Storage/ClipIndex.cs`), который перестраивается в фоне и правится инкрементально после каждой записи. Обхода диска перед сохранением клипа больше нет — раньше `EnsureSpace()` рекурсивно перечислял всю папку ровно в момент сохранения. Смена папки в настройках триггерит `Settings.Changed("storage")` → перестройка индекса по новой папке.
- **Потеря GPU-устройства** (TDR, обновление драйвера, смена GPU) распознаётся по HRESULT (`Core/Capture/DeviceLoss.cs`) и в колбэке кадра, и в вотчдоге захвата: конвейер пересобирается заново с паузами (объекты D3D после device removed мертвы навсегда), пользователь получает уведомление.
- **Одна копия приложения**: вторая копия не умирает молча, а сигналит первой именованным `EventWaitHandle` — та показывает окно и выходит на передний план.
- **Настройки применяются по одной модели**: вкладки «Запись» (видео и звук вместе) и «Клавиши и файлы» копят изменения до кнопки «Применить» — в строке состояния видно, что есть несохранённое; горячие клавиши и настройки приложения применяются сразу, и об этом написано на самой вкладке.
- **Своего плеера в приложении нет**: клик по клипу открывает его тем, что назначено в системе. Встроенный `MediaPlayerElement` зависел от тех же декодеров, что и любой плеер, а управление давал заметно хуже.
- **Файлы открываются через `explorer.exe`, а не прямым ShellExecute.** Приложение работает с правами администратора (требование манифеста), а из процесса с повышенными правами упакованные приложения Windows 11 («Фотографии», «Медиаплеер») активируются криво и рапортуют «не удаётся найти этот файл» на существующем файле. Explorer запускает обработчик с обычными правами пользователя.
- **Скриншот берёт кадр у работающего захвата.** WGC-источник по запросу копирует ближайший кадр в свою текстуру (`TryUseLatestFrame`); раньше он всегда отвечал «нет кадра», и скриншот на Windows 11 поднимал вторую сессию WGC — окно подвисало на секунды. Сжатие PNG вынесено из UI-потока, файл пишется одним куском из памяти.
- **Пипетка в снимке области берёт цвет из КАДРА, а не с экрана** (`Views/ColorSampling.cs`): поверх кадра лежат затемнение, уже нарисованные пометки и сама панель — с экрана она хватала бы их. Работает по всему кадру, а не только внутри выделения: подобрать оттенок с соседнего окна — обычное дело. После выбора сразу берётся карандаш, а значок пипетки красится в текущий цвет — иначе цвет, взятый с кадра, вообще негде увидеть: среди кружков палитры его нет.

- **Громкостей игры и микрофона в интерфейсе нет** — их регулируют системным микшером; из настроек звука остались источники, режим дорожек, устройства и шумодав с порогом в дБ.

## Тесты

```
dotnet test tests/InstantReplay.Tests/InstantReplay.Tests.csproj
```

Тест-проект (`net9.0`, xUnit) компилирует **исходники приложения напрямую** (`Compile Include`),
а не ссылается на него: сам проект — WPF-приложение под `net9.0-windows10.x`, и
`ProjectReference` притащил бы в тестовый хост весь графический стек. Поэтому покрывается
логика без зависимостей от UI: `HotkeyParser`, `HotkeyConflicts`, `ClipIndex`, `FileNaming`,
`ByteSize`, `ClipGrouping`, `ReplayBuffers`, `Log`, `ArenaMediaBuffer`, `UpdateVerification`.

То же самое гоняет CI (`.github/workflows/ci.yml`) на `windows-latest` при каждом пуше:
тесты, сборка приложения и проверка того, что три поля версии в csproj согласованы.

Тесты, которые появились не зря — каждый нашёл живую ошибку:

- `БезКлючевыхКадровБуферВсёРавноОграничен` — при единственном keyframe в начале
  (сломанный GOP) страховка вытеснения не срабатывала, и кольцевой буфер рос без предела.
- `FatalПопадаетВФайлПокаПишетФоновыйПоток` — `Log.Fatal` писал через `File.AppendAllText`,
  пока фоновый писатель держал тот же файл открытым. Оба открывали его с `FileShare.Read`,
  второй получал отказ, а пустой `catch` его глотал: все три глобальных обработчика падений
  писали в пустоту.
- `СчётчикиПартийНеЗависятДругОтДруга` — счётчик живых буферов арены был один на процесс,
  и следующее сохранение мешало предыдущему открепить блоки (см. `ArenaBufferBatch`).

## Выпуск новой версии (автообновление)

Обновления берутся только из официального репозитория проекта — он зашит
константой `UpdateService.Repo` (`Rizen1322/InstantReplay`), настройкой не меняется.

Всё делает `.\release.ps1` (патч по умолчанию, `-Bump minor|major`, `-DryRun` для плана).
Что происходит внутри и почему:

1. **Поднимается версия** в `src/Aura/Aura.csproj` — все три поля: `AssemblyVersion`,
   `FileVersion`, `Version`. Без этого обновление не предложится: сравнение идёт с
   версией сборки, и одинаковые версии считаются «уже последней».
   **Первые три числа `AssemblyVersion` обязаны совпадать с тегом релиза**
   (тег `v1.0.1` → `AssemblyVersion` = `1.0.1.0`). При `1.0.0.1` установленная
   версия считается старее собственного релиза, и он предлагается бесконечно.
   Это же соотношение проверяет CI.
2. Собирается установщик: `build_setup.ps1` → `dist\InstantReplaySetup.exe`.
3. Создаётся тег `vX.Y.Z` и релиз на GitHub, к нему прикладываются **два** файла:
   `InstantReplaySetup.exe` и `InstantReplaySetup.exe.sha256`.

Дальше приложение само: находит релиз новее текущей сборки, скачивает asset
(`.exe`/`.msi`/`.zip` — берётся первый подходящий) и запускает его с ключом
`/update <папка установки>`. В этом режиме установщик работает молча: гасит
приложение, обновляет файлы в той же папке и запускает новую версию.
Настройки, записи и выбор автозапуска не трогаются.

### Почему установщик проверяется перед запуском

Обновление запускает скачанный exe, а приложение работает с правами администратора.
Раньше единственной проверкой было «файл больше мегабайта» — то есть выполнялось всё,
что прилетело по ссылке. Теперь `Core/System/UpdateVerification.cs` требует три вещи:

1. ссылка ведёт на `github.com` или `*.githubusercontent.com` по HTTPS — чужой хост
   отбрасывается ещё до закачки;
2. файл начинается с сигнатуры PE — страница ошибки и обрезанный ответ CDN не пройдут;
3. SHA-256 совпадает с опубликованным в релизе. Слепок приезжает ответом `api.github.com`,
   а сам установщик — с `objects.githubusercontent.com`: подмена на стороне раздачи не
   проходит.

Четвёртый слой — **подпись ключом проекта**. Только он защищает от угона аккаунта
GitHub: слепок, выложенный злоумышленником, злоумышленник же и подпишет, а вот
подписать нашим ключом не сможет — закрытый ключ на GitHub не попадает никогда.

Включается один раз:

```
.\packaging\new_release_key.ps1
```

Скрипт создаёт пару ECDSA P-256, кладёт закрытую часть в `release-key.pem` (он в
`.gitignore`) и печатает открытую. Открытую вписать в константу
`UpdateVerification.PublicKeyBase64` и закоммитить — **закрытую сохранить вне
репозитория**.

Дальше `release.ps1` подписывает установщик сам (`openssl dgst -sha256 -sign`,
подпись едет в релиз файлом `InstantReplaySetup.exe.sig` в base64) и **отказывается
выпускать релиз без ключа** — проверка стоит до создания тега, чтобы не оставить
полурелиз с отправленным тегом.

Две вещи, о которых стоит знать заранее:

- **Потеря `release-key.pem` необратима.** Копии с вшитым старым открытым ключом не
  примут ни одного нового релиза, и обновиться можно будет только переустановкой
  вручную. Держите резервную копию вне рабочей папки.
- Пока константа пуста, подпись не требуется и релизы уходят с одной контрольной
  суммой — `release.ps1` предупреждает об этом жёлтым.

## Известные тонкости и что проверить при первом запуске

1. **Vortice API.** Код написан под Vortice 3.8.x. Имена методов и ключей MF в обёртке
   могут отличаться между версиями (`writer.Finalize()` у `IMFSinkWriter`, поля
   `OutputDataBuffer`, перегрузка `MediaFactory.MFTEnumEx`) — это первые кандидаты на
   правку компилятором при следующем обновлении. Проверять обновление лучше не сборкой,
   а запуском: сборка ловит только сигнатуры. Минимальный стенд — поднять
   `MediaFactory.MFStartup()`, `HardwareEncoders.ProbeSupport()`, создать устройство
   D3D11 и прогнать сотню NV12-кадров через `VideoEncoder`; этого хватает, чтобы задеть
   весь интероп, включая `ICodecAPI` и выдачу выходного типа с заголовками кодека.
2. **`H.NotifyIcon.Wpf` версии выше 2.3.2 брать нельзя,** пока приложение на .NET 9:
   в 2.4.x пакет содержит только `net10.0-windows` и `net462`, поэтому NuGet молча
   откатывается на сборку под .NET Framework (NU1701) — собирается, а работает как
   повезёт.
3. **AV1** доступен только на RTX 40+/RX 7700+/Arc; при отсутствии MFT энкодер честно кидает `NotSupportedException` — UI показывает диалог, выберите H264/HEVC.
4. **Оверлей поверх exclusive fullscreen** ОС не рисует в принципе (ShadowPlay делает это через собственный in-game hook). В borderless/windowed — работает везде; сама **запись** работает в любом режиме, включая exclusive fullscreen.
5. **Смешанные частоты дискретизации**: микшер приводит всё к 48 кГц stereo float (WDL-ресемплер NAudio).
6. Все настройки — `%LocalAppData%\Aura\settings.json`, логи — там же в `logs\`.
