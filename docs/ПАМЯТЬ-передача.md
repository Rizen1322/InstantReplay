# Рост памяти после сохранения — состояние расследования

Документ для продолжения в новой сессии. Всё ниже — измерено, не предположено.

## Симптом

После каждого сохранения повтора память процесса прибавляет 100–200 МБ и не
возвращает. Растёт до полки около 1.5 ГБ. Пользователь утверждает, что раньше
такого не было.

## Что уже исправлено (v1.1.83, коммит 404ce80)

**Обратное давление на писателя было мертво.** `ReplaySaver.WriteDrain` должен
притормаживать подачу, когда очередь SinkWriter превышает 64 МБ. Но
`IMFSinkWriter::GetStatistics` требует, чтобы поле `cb` структуры было заранее
заполнено её размером, а обёртка Vortice возвращает структуру по значению и `cb`
не заполняет — вызов падал с `E_INVALIDARG` **всегда**. `WriteDrain` ловил
исключение, помечал статистику недоступной и переставал тормозить вовсе.

Проверено живой пробой на настоящем Media Foundation:

| | результат |
|---|---|
| обёртка Vortice | `E_INVALIDARG (0x80070057)` |
| прямой вызов по vtable с `cb` | `HRESULT=0`, `SamplesReceived=20` (ровно подано), `ByteCountQueued=3 264 000` |

Исправлено прямым вызовом слота 13 vtable со структурой `SinkWriterStats`
(`ReplaySaver.cs`). В проекте это принятый приём — `CodecApi` так же обходит
обёртку для `ICodecAPI::SetValue`.

**Результат в логе** — механизм ожил:

```
было:  очередь писателя не видна — подача без ограничений
стало: очередь писателя: пик 67,6 МБ, ждали 485 мс
```

Очередь держится на 64 МБ вместо всего клипа (588 МБ). Сохранение не замедлилось:
1009 мс на 588 МБ.

## Что НЕ решилось

Память всё равно растёт. Замер вокруг двух сохранений после правки:

| | сборщик | нативная | частная |
|---|---|---|---|
| до сохранения 1 | 748 МБ | 509 МБ | 1258 МБ |
| после | 748 МБ | **682 МБ** | 1431 МБ |
| до сохранения 2 | 781 МБ | 731 МБ | 1512 МБ |
| после | 781 МБ | **867 МБ** | 1648 МБ |

**Управляемая память не меняется вовсе** — арену Кодекс починил верно (v1.1.82,
переиспользование блоков). Растёт только нативная.

## Ключевое наблюдение, которое ломает очевидную версию

Рост идёт **не во время сохранения**:

```
03:06:34  нативная 500   ← до
03:06:35  сохранение заняло 1 секунду
03:06:43  нативная 567
03:07:43  нативная 731   ← +164 МБ ЧЕРЕЗ МИНУТУ ПОСЛЕ
03:08:43  нативная 732   ← встало намертво
```

Сохранение длится секунду, а память прибавляет минуту спустя и замирает. Версия
«Media Foundation держит клип в очереди» этого не объясняет — иначе рост совпадал
бы с записью. Очередь к тому же теперь капнута на 67 МБ.

## Что проверено и ИСКЛЮЧЕНО

- **Очередь писателя** — 67 МБ, измерено в логе.
- **`ArenaMediaBuffer`** — vtable общая на процесс (`SharedVtbl`), экземпляры по
  40 байт, освобождаются в `Release`. 10 811 кадров = ~430 КБ, не 170 МБ.
- **Закрепление блоков арены** (`UnpinWhenWriterDone`) — отпускается, в логе нет
  предупреждения «писатель не отпустил … буферов за 30 секунд».
- **Миниатюры** — в логе вокруг этих сохранений их нет вообще.
- **Управляемая куча** — коммит сборщика стабилен через сохранение.

## Зацепка из карты памяти

Крупные частные области: `810 МБ` (это управляемая куча) и пара по `30 МБ`.
Значит ~800 МБ «нативной» размазаны по областям **мельче 16 МБ** — повадка
обычной кучи, а не одного большого блока (VirtualAlloc драйвера или своего
аллокатора).

## Что добавлено для следующего шага (не закоммичено)

`MemoryMap.cs` — раскладка частных областей. Новая строка в логе:

```
Частные области (до/после сохранения): всего N шт; до 1 МБ — X, 1–16 МБ — Y, от 16 МБ — Z
```

Читать так:
- **растёт ЧИСЛО областей** → живые выделения, настоящая утечка;
- **число стоит, объём растёт** → куча удерживает пик, новой памяти у системы не просит.

Это разные диагнозы с разным лечением. Без этих цифр их не различить.

## Осторожно: «нативная» — вычисляемое число

`нативная = частная − коммит сборщика`. Это не прямой замер. Если
`GC.GetGCMemoryInfo().TotalCommittedBytes` не учитывает какие-то сегменты
(например, удержанные из-за закрепления при сохранении), рост управляемой части
покажется нативным. Стоит перепроверить, прежде чем искать утечку в C++.

## Чем поможет бэкап до правок Кодекса

Пользователь предлагает папку с состоянием **до** изменений Кодекса. Логи
хранятся 7 дней, поэтому сравнить с «идеальным» состоянием начала сентября
нечем — бэкап это закрывает.

Что с ним сделать:

1. `git diff` бэкапа против текущего дерева по этим файлам:
   - `src/Aura/Core/Buffering/ReplayBuffers.cs`
   - `src/Aura/Core/Saving/ReplaySaver.cs`
   - `src/Aura/Core/Saving/ManualRecorder.cs`
   - `src/Aura/Core/Engine/ReplayEngine.cs`
2. Особое внимание — всему, что трогает `GCSettings.LatencyMode`
   (`SustainedLowLatency` подавляет обычные сборки второго поколения) и
   `ReleaseMemory()`.
3. Если бэкап собирается — прогнать на нём тот же сценарий (сохранить дважды) и
   снять те же цифры из лога. Это прямое сравнение «было/стало» вместо
   рассуждений.
