# Разбор: хук в игру, качество записи, скорость сохранения, размер папки

Всё ниже прочитано в коде и проверено по логам за 14 сентября.

## Что сделано

Все правки собраны, 446 тестов зелёные, нативный хук пересобран и прошёл проверку
раскладки протокола.

### Хук

- Время кадра переведено на `QueryPerformanceCounter`. `Stopwatch.GetTimestamp`
  в C# читает тот же счётчик, поэтому PTS с хука и PTS с Desktop Duplication
  теперь на одной шкале, а шаг 15.6 мс от `GetTickCount64` ушёл.
- Перед `glReadPixels` привязка буфера чтения сбрасывается в 0 и возвращается
  после. Чужой FBO игры больше не попадёт в запись.
- Очередь ошибок OpenGL очищается до чтения и проверяется после. Неудачное чтение
  теперь роняет кадр вместо публикации содержимого прошлого PBO как свежего.
- Кольцо PBO освобождается по запросу из потока отрисовки игры
  (`aura_gl_capture_request_release`), пока перехват ещё стоит. Раньше три буфера
  по размеру кадра оставались в контексте игры на каждый цикл остановки.
- Порядок снятия перехвата исправлен: отключение, ожидание выхода чужих потоков,
  только потом снятие трамплинов.

Переворот кадра на CPU оставлен как был. Я его предлагал убрать, но посчитал
точнее: строка кадра это 10 КБ, а на таком размере построчный `memcpy` идёт почти
со скоростью сплошного. Выигрыш был бы около десятой части одной копии, а сама
копия в 14.7 МБ на кадр никуда не девается — она встроена в схему с общей памятью.
Убирает её только совместное владение текстурой через `WGL_NV_DX_interop2`, и это
отдельная работа.

### Качество

- Битрейт переведён на `PeakConstrainedVBR`: средний равен заданному
  пользователем, потолок в полтора раза. Расчёт длины буфера повтора от этого не
  страдает, потому что средний битрейт режим соблюдает. Если энкодер режим не
  примет, чтение обратно это покажет и настройки откатятся на CBR с записью
  в лог.
- Режим низкой задержки стал управляемым. Он по-прежнему включается при старте,
  но после минуты спокойной работы `QualityAdapter` один раз за сеанс пробует его
  выключить: у NVENC это открывает просмотр вперёд и B-кадры. Первое же окно, где
  энкодер не успевает, возвращает режим обратно и закрывает вопрос до следующего
  запуска. Одна попытка вместо повторов выбрана намеренно: цена неудачи это одно
  окно в пять секунд.
- Для этого добавлен `CodecApi.SetDirectBool`: ключ объявлен булевым, а прямой
  вызов нужен, потому что решение принимается в потоке пейсера.

Проверить можно по строке `Битрейт по факту:` в логе. Там видно и режим, и
фактический средний битрейт, и состояние низкой задержки.

### Сохранение под нагрузкой

- Фоновый режим ввода-вывода теперь ограничен по времени. Первые 1500 мс клип
  пишется тихо, как раньше; если сохранение затянулось, режим снимается и остаток
  дописывается в полную силу. Приоритет процессора при этом остаётся `BelowNormal`,
  то есть у игры мы его не отбираем.
- Срок ожидания открепления блоков арены считается от размера клипа по полу
  в 15 МБ/с вместо постоянных 30 секунд.

Ожидаемый итог на клипе в 570 МБ: около 2.4 секунды вместо 14. В логе появится
строка «фоновый режим ввода-вывода снят».

### Папка

`.worktrees` уже удалены с диска, метаданные git подчищены через
`git worktree prune`. Ветки `codex/*` остались в репозитории; они влиты в `main`
и места не занимают.

Ниже исходный разбор, по которому делались правки.

## 1. Хук захвата (Minecraft, OpenGL)

### Что сделано хорошо

Протокол общей памяти (`game_hook_protocol.h`) собран аккуратно. Смещения всех полей
закреплены через `_Static_assert`, поэтому расхождение C и C# ловится на компиляции,
а не в бою. Три слота кадров с seqlock, счётчики heartbeat в обе стороны, `route_epoch`
и `capture_generation` для отбрасывания кадров от прошлой сессии, отдельный bootstrap
с nonce для подтверждения личности процесса. Это ровно то, что нужно.

Захват берётся ДО настоящего `SwapBuffers`, а не после. Это правильно: после свопа
содержимое заднего буфера по спецификации не определено.

Чтение кадра идёт через кольцо из трёх PBO с задержкой в два кадра
(`gl_capture.c`, `issued_count >= 3`). То есть `glReadPixels` не блокирует поток
отрисовки в ожидании GPU. Это правильный приём.

Захват берёт `TryAcquireSRWLockExclusive`, а не блокирующий вариант: поток отрисовки
игры никогда не встаёт в очередь за нашим замком. Тоже верно.

Хуки ставятся через MinHook на `SwapBuffers`, `wglSwapBuffers` и `wglSwapLayerBuffers`,
с проверкой на совпадение адресов и с защитой от рекурсии через `__declspec(thread)`.

### Что сделано неправильно

**Время кадра берётся из `GetTickCount64`.** В `gl_capture.c`:

```c
uint64_t now = GetTickCount64() * UINT64_C(10000);
```

Это число идёт и в паузу между кадрами, и в `slot->timestamp_100ns`, а оттуда через
`MinecraftGameCaptureSource.OnGameFrame` прямо в `CapturedSurface` как PTS кадра и
дальше в MP4.

Две беды сразу:

1. Разрешение `GetTickCount64` равно системному тику, по умолчанию 15.6 мс. Интервал
   кадра при 60 fps это 16.67 мс. Метки времени ложатся на грубую решётку, и в файле
   получается дёрганый ход кадров, даже когда игра шла ровно.
2. Остальной конвейер живёт на другом часовом источнике. `DesktopDuplicationSource`
   штампует кадры через `QpcToTicks(Stopwatch.GetTimestamp())`, то есть QPC. Гибридный
   захват Minecraft переключается между маршрутами GameLive и Monitor прямо во время
   записи (в логе это видно: `Minecraft route -> Monitor, epoch 3`). На каждом
   переключении PTS прыгает на разницу двух несогласованных шкал.

Правильно: `QueryPerformanceCounter` в хуке, приведённый к той же шкале, что и QPC
в C#. Это одна из тех правок, где выгода видна сразу.

**Вертикальный переворот кадра делается на CPU в потоке отрисовки игры.**
`publish_frame` копирует кадр построчно снизу вверх:

```c
for (int row = 0; row < state->height; ++row) {
    const uint8_t *source_row = pixels + (size_t)(state->height - 1 - row) * (size_t)state->stride;
    memcpy(destination + (size_t)row * (size_t)state->stride, source_row, (size_t)state->stride);
}
```

При 2560x1440 это 14.7 МБ на кадр, 884 МБ/с при 60 fps, и всё это отнимается у потока,
который рисует игру. Переворот бесплатно делается на стороне контроллера: либо
отрицательным шагом строки при загрузке в текстуру, либо флагом в шейдере NV12.
Копия в общую память нужна, переворот в ней — нет.

**Буфер чтения кадров не сбрасывается.** Код запрашивает текущий
`GL_READ_FRAMEBUFFER_BINDING` и тут же его выбрасывает:

```c
glGetIntegerv(GL_READ_FRAMEBUFFER_BINDING, &previous_read_framebuffer);
(void)previous_read_framebuffer;
```

Если игра оставила привязанным свой FBO на момент свопа, `glReadPixels` прочитает
его, а не задний буфер окна. Получится чужая картинка или мусор. Нужно привязать 0
на время чтения и вернуть прежнее значение.

**`aura_gl_capture_abandon` теряет PBO.** Функция обнуляет состояние через `memset`,
не удаляя буферы:

```c
void aura_gl_capture_abandon(void)
{
    AcquireSRWLockExclusive(&g_capture_lock);
    memset(&g_capture, 0, sizeof(g_capture));
    ReleaseSRWLockExclusive(&g_capture_lock);
}
```

Три PBO по 14.7 МБ остаются висеть в контексте игры до конца её работы. Удалить их
оттуда, откуда зовут, нельзя: это поток управления, а не поток отрисовки, и текущего
контекста у него нет. Значит, нужен флаг «удалить при следующем présent», а не тихая
потеря 44 МБ видеопамяти на каждый цикл остановки и запуска. В логах видно, что
маршрут захвата переключается часто, так что цикл повторяется.

**Порядок снятия хуков перевёрнут.** `hook_lifetime.c` сначала снимает хуки целиком,
и только потом ждёт, пока опустеет счётчик вызовов:

```c
aura_present_hooks_remove();
for (int attempt = 0; attempt < 200 && aura_present_hooks_active_callbacks() != 0; ++attempt) {
    Sleep(1);
}
```

А `aura_present_hooks_remove` внутри делает `MH_DisableHook`, `MH_RemoveHook` и
`MH_Uninitialize` подряд. То есть трамплины освобождаются ДО ожидания. Замысел в коде
верный, порядок неверный: ждать надо между `MH_DisableHook` и `MH_RemoveHook`.
MinHook при отключении замораживает потоки и уводит их указатели из трамплинов, так
что на практике это обычно проносит, но полагаться на это незачем.

**Ошибки OpenGL не проверяются.** Ни одного `glGetError`. Если `glReadPixels` не
прошёл, мы опубликуем содержимое старого PBO и не узнаем об этом. Плюс наши ошибки
остаются в очереди ошибок игры, а игры её читают.

### Архитектурный предел

Путь кадра сейчас такой: GPU, PBO, память процесса игры, общая память, динамическая
текстура D3D11, `CopyResource`, шейдер NV12, энкодер. Это две полные копии кадра
через CPU на каждый кадр, около 1.8 ГБ/с при 1440p60.

ShadowPlay и OBS так не делают. Для OpenGL есть `WGL_NV_DX_interop2`: контекст игры
получает доступ к текстуре D3D11, и кадр не покидает видеопамять вовсе. Копий через
CPU ноль. Это и есть причина, по которой у ShadowPlay нагрузка ниже.

Переход на interop — это не мелкая правка, но он снимает разом и нагрузку на поток
отрисовки, и переворот на CPU, и половину расхода памяти. Если хук будут расширять
на другие игры, делать это стоит до расширения, а не после.

### Область применения

Хук включается только для Minecraft и только после проверок:
`MinecraftHookEligibility`, `MinecraftProcessInspector`, `PortableExecutableInspector`
с разбором PE. Для остальных игр работают DDA и WGC, а они идут по GPU и всех
перечисленных издержек не имеют. То есть проблемы выше касаются пока только
Minecraft.

## 2. Качество записи против ShadowPlay

Сначала то, что сделано верно и подозревать не нужно.

**Цвет настроен правильно.** `VideoProcessorNv12` объявляет вход как full-range RGB
(`RGB_Range = 0`, `Nominal_Range = 0`), выход как BT.709 limited
(`YCbCr_Matrix = 1`, `Nominal_Range = 1`), автообработка выключена, и выходной
медиатип помечен теми же BT.709 и 16-235. Рассогласования шкал, от которого картинка
блёкнет или чернота слипается, здесь нет.

**Пресет качества уже максимальный.** В логе «пресет 33» выглядит низким числом, но
`QualityAdapter` читает у драйвера настоящий диапазон, а NVIDIA HEVC на RTX 3070
сообщает 0–33 и молча зажимает всё выше. 33 — это его потолок, а не наша скупость.

Теперь настоящие расхождения.

**Битрейт задан режимом CBR.** `ConfigureCodecApi` ставит
`AVEncCommonRateControlMode = 0`. В комментарии сказано, что так пишет NVIDIA App.
Это не так: ShadowPlay пишет переменным битрейтом, и потолок у него доходит до
130 Мбит/с.

Разница принципиальная. При CBR энкодер обязан выдавать 30 Мбит/с и на статичном
меню, и в момент взрыва на пол-экрана. На простой сцене биты уходят в никуда, на
сложной их не хватает, и появляются блоки — ровно там, где разницу и замечают.

В коде перебрали режим 3 (Quality) и отказались от него справедливо: там заданный
битрейт игнорируется вовсе, в замерах выходило от 15.0 до 58.1 Мбит/с. Но остался
непробованным режим 1, PeakConstrainedVBR: средний битрейт равен заданному
пользователем, а пик ограничен отдельным ключом. Это и есть поведение ShadowPlay.

Пробовать так: `AVEncCommonRateControlMode = 1`, `AVEncCommonMeanBitRate` = настройка
пользователя, `AVEncCommonMaxBitRate` = полтора-два от неё, `AVEncCommonBufferSize`
оставить как есть. Ключ `MaxBitRate` в логе перечислен среди поддерживаемых.

**Режим низкой задержки включён всегда.** `AVLowLatencyMode = true` стоит
безусловно. У NVENC это не только задержка: низкая задержка выключает просмотр вперёд
(lookahead), запрещает B-кадры и сажает буфер VBV. Всё это — прямая потеря качества
при том же битрейте.

Включено оно не от незнания: в комментарии записан замер, где без него MFT просил
только 39–44 кадра/с под игровой нагрузкой. То есть это обмен качества на то, чтобы
вообще держать 60 fps.

Обмен можно сделать умнее. `QualityAdapter` уже умеет отслеживать, справляется ли
энкодер, и переключать пресет на лету. Тем же механизмом можно начинать без режима
низкой задержки и включать его только когда энкодер действительно перестал успевать.
На RTX 3070 в большинстве игр он не понадобится.

**B-кадры выключены.** `AVEncMPVDefaultBPictureCount = 0`, и в комментарии сказано,
что на NVIDIA ключ всё равно не действует, потому что их запрещает режим низкой
задержки. Если снять режим низкой задержки, B-кадры станут доступны, а они дают
заметный выигрыш качества на том же битрейте.

Порядок действий, от большего эффекта к меньшему: сначала VBR с потолком, потом
режим низкой задержки по необходимости, потом B-кадры.

Чего через Media Foundation не достать вовсе: адаптивное квантование, просмотр
вперёд и двухпроходный режим. Список поддерживаемых ключей в логе их не содержит.
Эти три вещи у ShadowPlay есть, потому что он работает с NVENC напрямую. Полностью
догнать его, оставаясь на MFT, не выйдет; VBR и B-кадры закрывают основную часть
разрыва.

## 3. Сохранение под нагрузкой

Ответ: под игрой сохранение намеренно замедлено, и замедление большое.

В `ReplayEngine` поток сохранения понижается дважды:

```csharp
self.Priority = ThreadPriority.BelowNormal;
bool inGame = !string.Equals(game, "Desktop", StringComparison.OrdinalIgnoreCase);
using var backgroundIo = Saving.BackgroundIoScope.BeginIf(inGame);
```

`BackgroundIoScope` вызывает `SetThreadPriority` с `THREAD_MODE_BACKGROUND_BEGIN`.
В комментарии к нему сказано, что это опускает только приоритет дисковых операций.
На деле этот режим опускает и приоритет планировщика CPU, и приоритет памяти, и
приоритет ввода-вывода до самого низкого.

Что это даёт на практике, видно в логе за 14 сентября:

| условие | клип | время | скорость |
|---|---|---|---|
| рабочий стол | 570 МБ | 992 мс | 575 МБ/с |
| рабочий стол | 450 МБ | 842 мс | 535 МБ/с |
| под нагрузкой | 347 МБ | 8249 мс | 42 МБ/с |

Разница больше чем в десять раз. Замысел понятен и правильный: залп в сотни мегабайт
не должен отбирать диск у игры. Но 8 секунд вместо 0.6 — это уже другая крайность.

И есть следствие, которое опаснее медленного сохранения. `UnpinWhenWriterDone` ждёт
освобождения блоков арены не дольше 30 секунд:

```csharp
while (batch.Alive > 0 && clock.Elapsed < TimeSpan.FromSeconds(30))
```

Если ожидание истекло, блоки остаются закреплёнными НАВСЕГДА, и в лог идёт
предупреждение «писатель не отпустил ... буферов за 30 секунд». На 42 МБ/с
трёхминутный клип в 600 МБ пишется около 14 секунд. Запас до предела есть, но он
невелик, а при более тяжёлой сцене или медленном диске порог достижим. Тогда
приложение потеряет часть арены до перезапуска.

Что стоит сделать:

1. Разделить приоритеты. Фоновый режим Windows опускает поток слишком сильно.
   Для диска достаточно понижать только приоритет ввода-вывода, а приоритет CPU
   держать на `BelowNormal`, как и задумано строкой выше.
2. Считать срок ожидания от размера клипа и достигнутой скорости, а не брать
   постоянные 30 секунд.
3. Показывать в интерфейсе, что сохранение идёт медленнее обычного, раз это
   осознанный обмен.

## 4. Что удалить из папки

Всего в дереве около 10 ГБ. Настоящего исходного кода из них меньше 60 МБ.

| папка | размер | что это |
|---|---|---|
| `.worktrees` | 5.55 ГБ | три рабочих дерева git |
| `bin` и `obj` по всему дереву | 4.87 ГБ | результаты сборки |
| `dist` | 0.77 ГБ | собранный установщик и его промежуточные файлы |
| `.tools/zig-0.16.0` | 0.34 ГБ | компилятор для нативного хука |
| `.git` | 0.05 ГБ | сама история |

**`.worktrees` удаляются безопасно.** Все три ветки уже влиты в `main`, проверено
через `git branch --merged main`: `codex/cs2-external-pacing`,
`codex/minecraft-opengl-game-capture`, `codex/quality-size-optimization`. Ничего
неслитого там нет.

```bash
git worktree remove .worktrees/minecraft-opengl
git worktree remove .worktrees/quality-size-optimization
git worktree remove .worktrees/cs2-external-pacing
```

Если git откажется из-за незакоммиченных мелочей, добавить `--force`. Вернуть рабочее
дерево можно в любой момент одной командой `git worktree add`.

**`bin` и `obj` восстанавливаются сборкой.** `dotnet build` создаёт их заново.

**`dist` восстанавливается** запуском `build_setup.ps1`.

**`.tools/zig-0.16.0` восстанавливается** скриптом `packaging/get_zig.ps1`. Если
нативный хук пересобирается часто, папку лучше оставить: 0.34 ГБ против повторной
загрузки.

Итого без потерь освобождается около 9.5 ГБ.

Отдельно: папка `backup` из дерева уже исчезла. Внутри неё лежал архив
`InstantReplay.7z` на 716 МБ.
